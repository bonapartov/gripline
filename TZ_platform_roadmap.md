## 1. Обзор проекта

Gripline — платформа карт-федерации. Текущее состояние: сайт на Django + Wagtail с рейтингами пилотов, результатами соревнований, новостями.

**Цель развития:** полноценная платформа с мобильным приложением, персонализацией, автоматическим импортом данных с хронометража и аналитикой пилотов.

---

## 2. Принятые архитектурные решения

| Решение | Выбор | Обоснование |
|---------|-------|-------------|
| Мобильный стек | Flutter | Лучшая производительность, единый код для iOS/Android/Web |
| Backend API | FastAPI | Async, JWT из коробки, авто-документация Swagger |
| Авторизация | Вариант А1 — FastAPI читает Django `auth_user` | Единый логин для сайта и мобилки |
| Хранение данных | PostgreSQL — единый источник правды | Оба сервиса читают из одной БД, нет HTTP-зависимости |
| CMS | Django + Wagtail — остаётся | Хорошо делает одно: управление контентом |

### Итоговая архитектура

```
Apex Timing XML/webhook
         ↓
   ┌─────────────────────────────┐
   │        FastAPI              │
   │  • REST API для Flutter     │
   │  • JWT авторизация          │
   │  • ingestion данных         │
   │  • расчёт рейтингов         │
   │  • push-уведомления         │
   └─────────────────────────────┘
              ↕ SQL
         PostgreSQL
              ↕ SQL
   ┌─────────────────────────────┐
   │     Django + Wagtail        │
   │  • веб-сайт (SSR)           │
   │  • CMS (новости, статьи)    │
   │  • Wagtail admin            │
   └─────────────────────────────┘
              ↑ REST API
         Flutter App
```

## 3. Роли пользователей

| Роль | Что видит | Особенности |
|------|-----------|-------------|
| **Пилот** | Свой профиль, результаты, рейтинг, сравнение с соперниками | Привязан к `Driver` по ФИО (верификация администратором) |
| **Болельщик** | Лента подписок, результаты избранных пилотов | Подписка на любых пилотов |
| **Руководитель команды** | Все пилоты команды, их результаты и рейтинги | Привязан к `Team` |
| **Организатор** | Управление этапами, загрузка данных хронометража | На паузе, реализуется позже |

**Важно:** пользователь может иметь несколько ролей одновременно (например, пилот + руководитель команды). Роли подтверждённые на сайте автоматически активны в мобильном приложении.

## 4. Модель данных — новые поля и таблицы

### 4.1 Изменения в существующих моделях

#### `RaceClassResultGroup` — добавить поля:
```python
session_type = CharField(max_length=20, choices=[
    ('warmup',     'Прогрев'),       # тренировочная сессия, без очков
    ('qualifying', 'Квалификация'),  # таймированная сессия, задаёт сетку ABC-заездов
    ('heat',       'Заезд (ABC)'),   # round-robin заезды между группами A/B/C
    ('pre_final',  'Предфинал'),
    ('final',      'Финал'),
], default='final')
# default='final' корректен: все исторические записи — финалы

heat_group = CharField(max_length=10, null=True, blank=True)
# Группа заезда: 'AB', 'AC', 'BC'. Добавляем сейчас той же миграцией
# чтобы не трогать таблицу повторно на продакшне.
```

**Правила учёта сессий:**

| Тип сессии | Старты/победы/подиумы | История выступлений | Личные рекорды | BT-рейтинг |
|------------|----------------------|---------------------|----------------|------------|
| `warmup` | Нет | Нет | **Да** (источник чистых времён) | Нет |
| `qualifying` | Нет | Нет | **Да** | Нет |
| `heat` | Да | Да | Да | Да |
| `pre_final` | Да | Да | Да | Да |
| `final` | Да | Да | Да | Да |

Тип сессии определяется оператором при вводе данных — берётся из заголовка PDF-протокола Apex Timing.

#### `RaceResult` — добавить поля:
```python
start_position = IntegerField(null=True, blank=True)   # стартовая позиция
best_lap_ms    = IntegerField(null=True, blank=True)   # лучший круг, мс
best_s1_ms     = IntegerField(null=True, blank=True)   # лучший сектор 1, мс
best_s2_ms     = IntegerField(null=True, blank=True)   # лучший сектор 2, мс
best_s3_ms     = IntegerField(null=True, blank=True)   # лучший сектор 3, мс
```

Хранение в миллисекундах: нет проблем с округлением, идеальный круг = `best_s1_ms + best_s2_ms + best_s3_ms`.

### 4.2 Новое поле `best_lap_ms` vs идеальный круг

`best_lap_ms` — лучший **реальный** круг (один конкретный круг из гонки).  
**Идеальный круг** = `best_s1_ms + best_s2_ms + best_s3_ms` — теоретический минимум из лучших секторов разных кругов. Идеальный круг всегда ≤ лучшего реального круга.

В блоке «Личные рекорды» показывать оба числа раздельно с подписями — не путать.

### 4.3 Новая таблица `user_profile`

```python
class UserProfile(Model):
    user     = OneToOneField(AUTH_USER_MODEL, on_delete=models.CASCADE)
    roles    = ArrayField(CharField(max_length=20))  # ['pilot', 'manager']
    driver   = ForeignKey(Driver, null=True, blank=True, on_delete=models.SET_NULL)
    team     = ForeignKey(Team, null=True, blank=True, on_delete=models.SET_NULL)
    verified = BooleanField(default=False)
    # push_token — вынесен в отдельную таблицу PushToken (см. ниже)
```

> **Требование:** `django.contrib.postgres` должен быть в `INSTALLED_APPS` до создания миграции — `ArrayField` требует PostgreSQL и этот модуль. Добавить в `mysite/settings/base.py` перед Этапом 2.

**Синхронизация ролей с существующей системой сайта:**

В Django уже существуют модели `OrganizerProfile`, `TeamManager`, подтверждение пилота через `DriverClaim`. `UserProfile.roles` — это денормализованный кэш для FastAPI, он не является источником правды. Источник правды — существующие Django-модели.

Механизм синхронизации: Django-сигналы обновляют `UserProfile` атомарно — одним изменением проставляются и `roles`, и FK (`driver` / `team`) — при каждом изменении статуса в `DriverClaim`, `TeamManager` и т.д. Это гарантирует что после подтверждения пилота мобильное приложение сразу получает и роль `pilot`, и `driver_id` — сравнение с соперниками и личный профиль работают с первого запроса.

### 4.4 Новая таблица `push_token`

Одно поле `push_token` на профиле не работает при нескольких устройствах или переустановке приложения — новый токен молча перетирает старый.

```python
class PushToken(Model):
    user       = ForeignKey(AUTH_USER_MODEL, on_delete=models.CASCADE)
    token      = CharField(max_length=255, unique=True)
    created_at = DateTimeField(auto_now_add=True)
```

**Стратегия очистки мёртвых токенов:** накапливать все токены пользователя, не делать upsert. При отправке push FCM возвращает `InvalidRegistration` или `NotRegistered` для недействительных токенов — по этому ответу запись удаляется. Это стандартный паттерн push-сервисов: не требует `device_id` на стороне Flutter, не зависит от Keychain/Keystore, работает при переустановке автоматически.

## 5. Страница пилота — что добавляется

### 5.1 В таблице «История выступлений»

| Элемент | Где | Описание |
|---------|-----|---------|
| Тип сессии | Бейдж в ячейке «Соревнование» | `Ф` / `Пф` / `ПР` — маленький цветной бейдж |
| Прогресс позиции | Под позиционным бейджем | Например: `5→2 ▲3` (если данные есть) |
| Лучший круг | Новая ячейка | `1:02.347` (если данные есть) |

### 5.2 Новый блок «Личные рекорды»

Размещение: между блоком «Статистика пилота» и таблицей истории.

Содержимое:
- Лучший круг по каждому классу (абсолютный рекорд)
- Лучшие секторы S1 / S2 / S3
- Идеальный круг (сумма лучших секторов)
- Отображается только если данные есть, иначе блок скрыт

## 6. FastAPI — эндпоинты

### Авторизация
```
POST /auth/login          → JWT access + refresh токены
POST /auth/refresh        → обновление access токена
POST /auth/logout         → инвалидация токена
GET  /auth/me             → профиль текущего пользователя
PUT  /auth/me             → обновление профиля
POST /auth/link-driver    → запрос на привязку к Driver (для пилотов)
```

### Пилоты
```
GET  /pilots              → список пилотов (с фильтрами по классу)
GET  /pilots/{id}         → профиль пилота
GET  /pilots/{id}/results → история результатов
GET  /pilots/{id}/rating  → рейтинг по классам
```

### Чемпионаты и результаты
```
GET  /championships              → список чемпионатов
GET  /championships/{id}         → детали чемпионата
GET  /championships/{id}/stages  → этапы чемпионата
GET  /stages/{id}                → результаты этапа
```

### Команды
```
GET  /teams          → список команд
GET  /teams/{id}     → профиль команды с пилотами
```

### Персонализированная лента
```
GET  /feed                      → лента текущего пользователя (по роли)
GET  /subscriptions             → подписки болельщика
POST   /subscriptions/{pilot_id}  → подписаться на пилота
DELETE /subscriptions/{pilot_id}  → отписаться
```

### Контент (читаем из Wagtail БД)
```
GET  /news          → список новостей
GET  /news/{id}     → статья
GET  /articles      → матчасть
```

### Ingestion (организатор, на паузе)
```
POST /admin/import/results  → загрузка XML/CSV с хронометража
POST /admin/recalc-ratings  → запуск пересчёта рейтингов
```

## 9. Тестирование

### Среды

```
Локальная машина (dev) → GitHub → Продакшн (cherry-pick)
```

**Локальная машина** выполняет роль staging — все изменения тестируются здесь перед отправкой на сервер.

### Настройка локальной среды

```bash
# Клонировать репозиторий
git clone https://github.com/bonapartov/gripline.git
cd gripline

# Создать виртуальное окружение
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt

# Настроить локальную БД — только PostgreSQL (SQLite не поддерживает ArrayField)
cp mysite/settings/dev.py.example mysite/settings/dev.py
# Отредактировать dev.py — указать локальную PostgreSQL БД

# Применить миграции
python manage.py migrate

# Запустить
python manage.py runserver
```

### Что тестировать перед каждым деплоем

| Этап | Проверка | Как |
|------|----------|-----|
| Миграции | Применяются без ошибок | `python manage.py migrate` локально |
| Admin | Новые поля видны в Wagtail admin | Открыть локально, создать тестовую запись |
| Шаблоны | Страница пилота отображает новые данные | Браузер, локальный runserver |
| FastAPI | Эндпоинты отвечают корректно | Swagger UI (`/docs`) |
| Flutter | Приложение получает данные от API | Эмулятор или реальное устройство |

### Автотесты (минимальный набор)

Покрывать автотестами только критичную логику без UI:

1. **Расчёт рейтинга** (`analytics/bradley_terry/`) — unit-тесты: входные данные → ожидаемый рейтинг
2. **FastAPI эндпоинты** — интеграционные тесты: авторизация, доступ по ролям, структура ответов

### Деплой на продакшн

```bash
# Локально: убедиться что тесты проходят, страницы работают
# Закоммитить и запушить на рабочую ветку
git push origin <рабочая-ветка>

# На сервере:
git fetch origin
git cherry-pick <hash>
python manage.py migrate   # если есть миграции
systemctl restart gripline
```
