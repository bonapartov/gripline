# Синхронизация SetupKart: подтверждения записей

Изменения сервера и клиента готовятся совместно. API остаётся Django
`/api/setupkart/` (порт 8002). FastAPI `/api/mobile/` в этом обмене не участвует.

## Отправка

Запрос содержит прежние `schema_version`, `tables` и новый `protocol_version: 2`.
Ответ сохраняет `accepted`/`skipped` и добавляет `protocol_version: 2`, `results`.
Без нового параметра ответ остаётся прежним, для установленных клиентов.

Каждой строке соответствует подтверждение в порядке таблиц
`karts`, `engines`, `tracks`, `sessions` и строк внутри таблицы:

```json
{"table":"sessions","id":"uuid","updated_at":1760000000000,"status":"accepted"}
```

Статусы: `accepted` (сохранена), `unchanged` (повтор), `server_newer`
(на сервере новее; клиент затем получает актуальную запись), `rejected`
(с причиной `invalid_record`, `draft`, `row_too_large`, `record_limit`, `newer_schema`).
Старая схема не может заменить запись более новой схемы.

Клиент проверяет идентификатор, таблицу и время каждой квитанции. Неполный,
неизвестный или старый ответ не подтверждает отправку. При отказе указатель
отправки остаётся прежним; повторная отправка уже принятых строк безопасна.
Запросы одного аккаунта сериализуются блокировкой его строки в PostgreSQL.

## Получение и обновление приложения

Курсор серверный: время изменения + ID. Все страницы собираются до объединения,
чтобы родители существовали к моменту вставки сессий. При несовместимой схеме
вся полученная партия с зависимостями сохраняется в настройках локальной БД.
Очередь и курсор записываются одной транзакцией. Когда схема станет доступна,
партия объединяется и очередь очищается той же транзакцией.

Однократно для исправления старых пропусков, затем при изменении версии схемы,
курсор сбрасывается: сервер повторно отдаёт историю без удаления локальных данных.
Это восстанавливает записи, пропущенные прежним клиентом, если они остались на сервере.

Смена аккаунта очищает очередь, курсор восстановления и прежний статус.
Время успешной синхронизации меняется только после успешного полного обмена
без отложенных записей; ошибки сохраняются и отображаются в аккаунте.

## Проверка и выпуск

Сначала сервер с обратной совместимостью, затем приложение. Новому клиенту нужен
сервер с квитанциями: старый сервер приведёт к явной незавершённой синхронизации,
указатель отправки сохранится для повтора после обновления сервера.
Миграции БД для этого этапа не требуются.

Регрессии: частичный приём и повтор, потерянный ответ, HTTP-ошибка получения,
несовместимая схема и повторная обработка очереди, смена аккаунта, страницы
с зависимостями, удаления, изоляция аккаунтов. Серверные тесты —
`website/tests/test_setupkart_sync.py`, клиентские — `test/session_sync_test.dart`.

## Следующие этапы

Оптимистические серверные ревизии и разрешение конфликтов пользователем,
полная изоляция локальных данных по аккаунтам, разгрузка экрана/контроллера сессии.
В текущем протоколе выбор версии по-прежнему основан на `updatedAt` телефона;
квитанции не заменяют механизм разрешения конфликтов.
