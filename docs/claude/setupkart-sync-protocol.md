# Синхронизация SetupKart: подтверждения записей

Изменения сервера и клиента готовятся совместно. API остаётся Django
`/api/setupkart/` (порт 8002). FastAPI `/api/mobile/` в этом обмене не участвует.

## Отправка

Запрос содержит прежние `schema_version`, `tables` и новый `protocol_version: 2`.
Ответ сохраняет `accepted`/`skipped` и добавляет `protocol_version: 2`, `results`.
Без нового параметра ответ остаётся прежним, для установленных клиентов.

Каждой строке соответствует подтверждение в порядке таблиц
`karts`, `engines`, `tracks`, `sessions` и строк внутри таблицы:

```json
{"table":"sessions","id":"uuid","updated_at":1760000000000,"status":"accepted"}
```

Статусы: `accepted` (сохранена), `unchanged` (повтор), `server_newer`
(на сервере новее; клиент затем получает актуальную запись), `rejected`
(с причиной `invalid_record`, `draft`, `row_too_large`, `record_limit`, `newer_schema`).
Старая схема не может заменить запись более новой схемы.

Клиент проверяет идентификатор, таблицу и время каждой квитанции. Неполный,
неизвестный или старый ответ не подтверждает отправку. При отказе указатель
отправки остаётся прежним; повторная отправка уже принятых строк безопасна.
Запросы одного аккаунта сериализуются блокировкой его строки в PostgreSQL.

## Получение и обновление приложения

Курсор серверный: время изменения + ID. Все страницы собираются до объединения,
чтобы родители существовали к моменту вставки сессий. При несовместимой схеме
вся полученная партия с зависимостями сохраняется в настройках локальной БД.
Очередь и курсор записываются одной транзакцией. Когда схема станет доступна,
партия объединяется и очередь очищается той же транзакцией.

Однократно для исправления старых пропусков, затем при изменении версии схемы,
курсор сбрасывается: сервер повторно отдаёт историю без удаления локальных данных.
Это восстанавливает записи, пропущенные прежним клиентом, если они остались на сервере.

Смена аккаунта очищает очередь, курсор восстановления и прежний статус.
Время успешной синхронизации меняется только после успешного полного обмена
без отложенных записей; ошибки сохраняются и отображаются в аккаунте.

## Проверка и выпуск

Сначала сервер с обратной совместимостью, затем приложение. Новому клиенту нужен
сервер с квитанциями: старый сервер приведёт к явной незавершённой синхронизации,
указатель отправки сохранится для повтора после обновления сервера.
Для v2 миграции БД не требовались; v3 добавляет `server_revision` (миграция
`0112`), поэтому сервер выпускается первым.

Регрессии: частичный приём и повтор, потерянный ответ, HTTP-ошибка получения,
несовместимая схема и повторная обработка очереди, смена аккаунта, страницы
с зависимостями, удаления, изоляция аккаунтов. Серверные тесты —
`website/tests/test_setupkart_sync.py`, клиентские — `test/session_sync_test.dart`.

## Серверные ревизии и конфликты (v3, 16.11.2026)

Сервер хранит `AppSyncRecord.server_revision` (миграция
`website.0112_appsyncrecord_server_revision`): 1 при создании, +1 при каждом
принятом изменении, включая удаление. Ревизия — версия содержимого строки, а не
время; она не меняется от переключателей видимости в ЛК, потому что они не
затрагивают `data`.

Клиент включает новый режим, присылая `protocol_version: 3` и карту
`revisions` — ревизию, на которой основана каждая правка:

```json
{
  "protocol_version": 3,
  "schema_version": 9,
  "revisions": {"sessions|uuid": 4, "karts|uuid": 1},
  "tables": {"sessions": [{"id": "uuid", "updatedAt": 1760000000000, "...": "..."}]}
}
```

Ключ — `<table>|<id>`. Если ревизии для строки нет (первая отправка после
обновления приложения), сервер применяет прежнее правило `updatedAt` и всё
равно возвращает новую ревизию в квитанции. Клиент сохраняет её для следующих
отправок.

Ответ v3 сохраняет `accepted`/`skipped`, добавляет `protocol_version: 3` и
`results`. Каждая квитанция содержит `revision` — текущую серверную ревизию
строки после обработки:

```json
{"table":"sessions","id":"uuid","updated_at":1760000000000,
 "status":"conflict","revision":5,"row":{"id":"uuid","updatedAt":1760000001000,"...":"..."}}
```

Статусы:

- `accepted` — запись сохранена, `revision` новая;
- `unchanged` — на сервере уже ровно эта строка (повтор после потерянного
  ответа), ревизия не менялась;
- `server_newer` — присланная правка старше серверной по `updatedAt`, серверная
  строка не изменена; клиент получит её при следующем pull;
- `conflict` — присланная `base_revision` не совпала с текущей серверной
  ревизией; сервер **ничего не перезаписал**, вернул текущую строку в `row` и
  её `revision`;
- `rejected` — как раньше, с причиной (`invalid_record`, `draft`,
  `row_too_large`, `record_limit`, `newer_schema`).

Разрешение конфликта: клиент сохраняет обе стороны (локальную правку и
серверную строку из `row`), показывает выбор пользователю, затем повторяет
отправку выбранной версии с `base_revision` = `revision` из конфликтной
квитанции. Если пользователь выбрал серверную версию, локальная заменяется без
отправки. Удаления — такие же строки с `deletedAt`: конфликт возникает и при
попытке изменить удалённую на сервере строку, и при попытке удалить изменённую.

`pull` теперь отдаёт `revision` рядом с `schema_version` и `row`. Для
установленных клиентов это дополнительное поле, которое они игнорируют; форма
ответа v1/v2 не менялась, квитанции v2 по-прежнему без `revision`.

Порядок выпуска: сначала сервер (эта миграция и код), затем клиент с v3.
Сервер принимает и старые протоколы без изменений. В этом этапе клиентское
приложение не обновлялось: APK на телефоне проверяет совместимость с сервером.

Регрессии v3: совпавшая и устаревшая ревизия, повтор после потерянного ответа,
разрешение конфликта текущей ревизией, одновременные правки, удаление против
правки в обе стороны, первая отправка без `revisions`, новые строки,
неизменность квитанций v2. Серверные тесты —
`website/tests/test_setupkart_sync.py`.
