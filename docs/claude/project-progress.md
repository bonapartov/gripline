## Границы секторов схемы Пластунки исправлены (04.11.2026)

На странице трассы Пластунка 3D-метка отказывалась ехать: «Время секторов
не сходится со схемой трассы — метка не едет». Причина — проверка
правдоподобия в `track_3d.js` (после инцидента на Лемаре со S3 = 3 с):
средняя скорость сектора по нарисованной схеме не должна превышать
120 км/ч (130 для KZ/DD2). Метки границ на схеме стояли «третями»
(s1s2=0.33, s2s3=0.67), из-за чего S3 получал 30 % длины круга, и лучшее
время S3 давало 123–145 км/ч у всех шести классов — проверка блокировала
все классы трассы.

Пользователь не знает фактического расположения линий секторов на трассе,
поэтому выбран оценочный вариант: границы пропорционально времени секторов
(доля времени = доля длины). По лучшим секторам шести классов RM доли
времени почти идентичны: S1 45.4 %, S2 35.9 %, S3 18.7 %. Новые границы:
`s1s2=0.424`, `s2s3=0.783` (start 0.97 не менялся), round до 3 знаков.
После правки все классы проходят проверку со средними 78–91 км/ч.

- Перед правкой создан и проверен бэкап:
  `/var/backups/gripline/gripline_db_before_plastunka_scheme_20261104T193951Z.dump`
  (11 368 489 байт; SHA256
  `e3cbc0022c9582a5eea23a74c58acef61d60f99c6994617a1d4264d5df9432c5`).
- Правка через ORM (`Track.scheme_data` + `save()` — сохранение
  перегенерирует `scheme_svg`; сырой SQL не годится). Значения на живой
  странице подтверждены, схема и scheme.pdf отвечают 200.
- Оценочность: допущение «средняя скорость по всем участкам одинакова» —
  S3 по времени быстрый (прямая), поэтому его реальная доля длины может
  отличаться от 18.7 %. Если узнать фактические линии секторов у
  организатора — поправить метки в редакторе схемы (админка → Трассы),
  проверка 3D подхватит автоматически. Заодно с границами обновились
  диапазоны поворотов по секторам в таблице страницы (считаются от меток).

## Дубль сайта под cleantogo.ru закрыт (02.11.2026)

Google показывал страницы Gripline в поиске под доменом `cleantogo.ru`
(например «Схема трассы — Пластунка» с PDF). Домен пользовательский, к сайту
отношения не имеет, но указывает A-записью на тот же сервер: nginx отвечал
сайтом на любой Host, а `ALLOWED_HOSTS` в prod.py явно разрешал
`cleantogo.ru` и `www.admin.cleantogo.ru`. Сертификат на сервере только для
gripline.ru, поэтому браузеры видели ошибку SSL, а Googlebot проиндексировал
дубль несмотря на неё.

Исправление (коммит `ad48de3`, задеплоен):

- `mysite/settings/prod.py`: домены cleantogo убраны из `ALLOWED_HOSTS`,
  осталось `['gripline.ru', 'www.gripline.ru']`; Django отвечает 400 на чужой Host.
- nginx: добавлен catch-all `deploy/nginx/catchall.conf` (443 + 80,
  `default_server`, 301 на `https://gripline.ru$request_uri`), установлен
  в `/etc/nginx/sites-enabled/catchall`. Сертификат gripline.ru в 443-блоке —
  только чтобы рукопожатие завершилось и краулер получил 301.
- Проверки после: cleantogo.ru (HTTP и HTTPS, включая scheme.pdf) и
  произвольный чужой хост — 301 на gripline.ru; главная, www,
  `/api/setupkart/config/`, `/tracks/plastunka/scheme.pdf` на gripline.ru — 200;
  Django напрямую с `Host: cleantogo.ru` — 400.
- БД не затронута, миграций нет. Выдача Google переклеится по 301 за
  несколько дней–недель. Если cleantogo.ru понадобится под свой сайт —
  добавить ему собственный server-блок, он перехватит трафик раньше catch-all.

## Что выполнено в первом этапе

1. Сервер принимает `protocol_version: 2` и возвращает квитанцию каждой строки:
   таблица, ID, время изменения, статус и причина отказа. Для старых клиентов
   сохранён прежний формат ответа.
2. Клиент проверяет каждую квитанцию. При частичном отказе, неправильной
   квитанции или старом формате ответа указатель отправки не продвигается;
   данные доступны для повторной отправки.
3. Загрузки несовместимой схемы сохраняются в локальной БД вместе с зависимостями.
   Очередь и курсор фиксируются одной транзакцией. После обновления схемы
   приложение обрабатывает очередь; это проверено на файле SQLite после закрытия
   и повторного открытия базы.
4. Добавлено однократное повторное получение истории с сервера для восстановления
   записей, пропущенных старым клиентом; восстановление повторяется при смене
   версии схемы.
5. Время успешной синхронизации меняется только после полного успешного обмена.
   Ошибка или ожидание обновления сохраняются и показываются в аккаунте.
6. Смена аккаунта очищает отложенные загрузки и предыдущий статус синхронизации.
   Это ещё не полноценная изоляция всех локальных данных по аккаунтам.
7. Устранено окно одновременного запуска клиентской синхронизации; серверные
   загрузки одного аккаунта сериализуются блокировкой пользователя в PostgreSQL.
8. Старый клиент не может перезаписать запись более новой схемы.
9. В Smart Setup уточнено, что сравнение прошлых сессий не доказывает причину
   улучшения времени. Пояснения температуры, другого карта и пилота уже были
   в интерфейсе.

Подробный контракт: [setupkart-sync-protocol.md](setupkart-sync-protocol.md).
Копия контракта в мобильном репозитории: `docs/sync-protocol.md`.
