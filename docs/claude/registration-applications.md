## Заявки пилотов и команд: уведомления (реализовано 2026-10-07)

`DriverClaim` (привязка к пилоту) и `TeamClaim` (управление командой) — обе проходят ручное подтверждение админом в Wagtail («Заявки пилотов», «Заявки команд»: `status` → `approved`).

- **Админу** о новой заявке (`status='pending'` при создании) — `website/claim_notify.py::notify_admins_new_claim`: письмо на `MailSettings.admin_notify_email` (ссылка на саму заявку в админке) + сообщение в админ-чат Telegram (`feedback/notify.py::notify_admin_chat`, работает без процесса бота). Вызывается из `post_save`-сигналов (`accounts/signals.py`, `teams/signals.py`) через `transaction.on_commit` — **во views уведомлять не нужно и нельзя**: новая точка входа, создающая заявку, уведомит админа сама (раньше было 11 ручных вызовов, и любой забытый оставлял заявку незамеченной). Заявки, созданные сразу `approved` (demo/скрипты), админа не будят.
- **В Telegram — без ПД:** только тип, название команды (у пилота — вообще без имени: во флоу «новый пилот» это ещё не опубликованный человек) и ссылка. E-mail и имя заявителя только в письме.
- **Заявителю:** пилот — `claim_pending/approved/rejected`; команда — `team_claim_pending/approved/rejected` (те же шаблоны макета). Письма уходят только при **смене** статуса (`pre_save` запоминает `_old_status`). «Подтверждена» у команды — только когда выбрана `team` (иначе `TeamManager` не создаётся и роль не выдаётся): если админ выбрал команду позже статуса, письмо уходит в этот момент.
- **Подтверждение email (с 07.10.2026, единое для пилота/команды/организатора):** регистрация по email создаёт активный аккаунт с `UserProfile.email_verified=False`; войти (сайт, кабинеты, FastAPI `/auth/login` и `/auth/refresh` — 403) можно только после перехода по ссылке из письма (`accounts/verification.py`, ссылка живёт 30 мин, `PASSWORD_RESET_TIMEOUT`). `User.is_active=False` теперь значит только «заблокирован» — ссылка из письма и «повторное письмо» заблокированный аккаунт НЕ оживляют (раньше is_active был и баном, и «не подтверждён» — бан обходился). Повторная отправка отвечает одинаково для любого адреса (нет перебора адресов). Существующим пользователям миграция `accounts.0012` проставила `email_verified=True`; социальные входы (Яндекс/VK/Telegram) — True по умолчанию. **Заявка пилота/команды и уведомление админу появляются только после подтверждения email** (спам-регистрации админа не будят); данные для заявки берутся из БД (`User.first/last_name`, `UserProfile.city`, `UserProfile.pending_team_name`), не из сессии — ссылку можно открыть в другом браузере. Если после подтверждения есть однофамильцы/похожие команды — переход на вход с `?next=` на `select_driver`/`select_team` (они `@login_required`, считают кандидатов по БД для `request.user`); админу тогда уходит «Новая регистрация пилота (профиль не выбран)».
- **Менеджер команды только после одобрения (с 07.10.2026):** Яндекс-флоу «новая команда» больше не создаёт `Team` и `TeamManager` — только `TeamClaim(team=None, requested_team_name, requested_city)`. При `approved` без выбранной админом команды сигнал (`teams/signals.py`) сам создаёт `Team` (slug уникализируется) и менеджера-капитана; при `rejected` — деактивирует менеджера этой команды (старые заявки, где он был выдан заранее) и роль уходит из профиля. Админу, подтверждающему заявку на «дубль» существующей команды, достаточно выбрать её в поле `team`.
- **Баг, найденный тестом пути регистрации:** `accounts/views.py::register` вызывал `login(request, user)` без `backend` — при нескольких `AUTHENTICATION_BACKENDS` Django бросает `ValueError` → 500 на любой регистрации по email (на проде 02.10.2026 в журнале ровно одна такая ошибка). Исправлено явным `backend='django.contrib.auth.backends.ModelBackend'`. Остальные `login()` идут после `authenticate()` и безопасны.
- **Регистрация пилота без заявки:** если при регистрации по email в базе есть однофамильцы, заявки нет, пока человек не выберет профиль (закрыл страницу — админ не узнал бы). `claim_notify.notify_admins_registration_without_claim` шлёт письмо + Telegram «Новая регистрация пилота (профиль не выбран)» со ссылкой на пользователя в Wagtail (`/admin/users/edit/N/`); без совпадений уведомление только о заявке (дубля нет).
- **Прибрано попутно:** namespace `teams` был занят дважды (`teams.urls` и сниппет-вьюсет в `website/urls.py`; второй был перекрыт и недостижим по имени) → второй переименован в `team_snippet`, `urls.W005` ушёл; из `verify_email` удалена мёртвая ветка с `pending_*` (ключи сессии нигде не ставятся) — сам обработчик нужен: на него ведёт вход неактивного аккаунта («запросить новое письмо»); город из формы «новая команда» (Яндекс-онбординг) теперь сохраняется в `Team.city` (раньше читался и терялся).
- Тесты: `website/tests/test_claim_notify.py` (все пути создания заявки → ровно одно письмо и одно сообщение).
- **Security-ревью регистраций (07.10.2026, агент по безопасности, локально) → исправлено:** (1) stored XSS — `{{ team.description|safe }}` выводил текст, который менеджер команды правит в ЛК; теперь везде для пользовательских `description`/`biography` фильтр `|safe_html` (`website_tags.py`, nh3: простая разметка, без скриптов/обработчиков/`javascript:`; пустое → `''`, чтобы работал `|default:`) — **не возвращать `|safe` на этих полях** (страж-тест `test_user_editable_texts_never_use_plain_safe_filter`); (2) `ratelimit_post` (`services/balance_limits.py`) — лимит только на POST: регистрация пилота/команды 20/час с IP, повторная отправка письма 10/час; (3) повторное открытие ссылки подтверждения команды больше не плодит `TeamClaim`; (4) `select_driver`/`select_team` принимают только id из найденного при регистрации списка; (5) `Team.save()` — уникальный slug с суффиксом (раньше 500 при одноимённых командах); (6) тексты исключений SMTP/дашборда не показываются пользователю; (7) `verification_resend.html` пересохранён в UTF-8 (был cp1251 → 500).
- **Закрыто тем же вечером** (см. пункты выше): менеджер до одобрения, обход бана через `verify_email`/resend, регистрация пилота без подтверждения email. **Занятый email на регистрации (пилот/команда/организатор):** форма отвечает так же, как для нового адреса (тот же редирект и сообщение — по тексту ответа адреса не перебрать); владельцу адреса уходит письмо: подтверждённому — `account_exists` («вы уже зарегистрированы», ссылки на вход и восстановление пароля), неподтверждённому — новая ссылка подтверждения, заблокированному — ничего (`accounts/verification.py::handle_existing_email`, регистр адреса не важен; проверка идёт после валидации формы — невалидная форма существование адреса тоже не выдаёт). **Профиль «нового пилота» создаётся только при одобрении:** Яндекс-флоу «новый пилот» и регистрация по email без однофамильцев создают лишь `DriverClaim(driver=None, requested_*)`; при `approved` без выбранного админом пилота сигнал (`accounts/signals.py::_create_driver_for_approved_claim`) сам создаёт `Driver` (уникальный slug, город из заявки) и привязывает его. До этого публичной страницы пилота нет, при отказе ничего не остаётся. Админу, подтверждающему заявку на уже существующего пилота, достаточно выбрать его в поле `driver` — иначе получится дубль без результатов.

## Регистрация на этап: мастер, УТС, отзыв (реализовано 2026-10-14)

- **Мастер** `applications/wizard.py` (+ `wizard_forms.py`, шаблон `applications/wizard.html`): `/applications/apply/<stage>/` продолжает черновик, шаги `.../step/1..5/` — ① участие (УТС) + класс + номер → ② пилот → ③ карт, механик, заявитель → ④ опции → ⑤ проверка и отправка. Черновик (`Application.status='draft'`, `wizard_step`) сохраняется после каждого шага, номер бронируется с шага ① и держится **12 часов после последнего сохранения шага** (`applications.models.DRAFT_HOLD`, `Application.holding_q()` — единственное место правила; брошенный черновик не держит ни номер, ни место в лимите, но не удаляется: вернувшись, человек продолжит, если номер свободен, иначе выберет другой); перескочить вперёд нельзя. Организатору черновики не показываются (только их число). Старая длинная форма удалена.
- **Без входа:** гость проходит ① (данные в сессии), на ② оставляет email → учётка со **случайным** паролем (без пароля Django не шлёт письмо сброса) + автологин; пароль — через «Забыли пароль?». Занятый email → «войдите», шаг ① сохраняется. `VerifyingPasswordResetConfirmView` отмечает email подтверждённым при сбросе.
- **Новый пилот / новая команда** → `DriverClaim` / `TeamClaim` создаются **только при отправке** (шаг ⑤): срабатывают существующие сигналы — Telegram админ-чат, письма pending/approved/rejected. Совпало имя с пилотом в базе — выбор «это я» (`ApplicationPilot.requested_driver` → claim на этого пилота). Команда не из списка — `ApplicationApplicant.new_team_*`, claim на контакт (после одобрения — менеджер). При одобрении `applications/signals.py` привязывает заявки (`driver_claim` → `driver`, `team_claim` → `team`); сигналы accounts/teams импортируются в `ApplicationsConfig.ready()` раньше своих — иначе привязка сработала бы до создания Driver/Team.
- **Документы и квитанция** — догружаются после отправки; организатор видит «не полные».
- **Отзыв** (`applications:cancel`, только POST, до начала этапа): статус «Отозвана», `withdrawn_at`/`withdraw_reason`, номер освобождается, письмо организатору; возврат взноса — вне системы.
- **УТС** (опция этапа): `Stage.has_training`, `training_fee`, `training_start`, `training_number_digits`; участие `Application.participation` (только этап / УТС + этап / только УТС). Правила — `Stage.number_range()`, `fee_for()`, `separate_training_numbers()`: формат номеров УТС совпадает с этапом — база общая, иначе свой диапазон. Лимит участников — только едущие этап. Отдельные классы этапа (не как у чемпионата) — не делаем (решение 15.10.2026).
- **Формы сайта:** `static/website/js/custom.js` — календарь открывается кликом по полю (`showPicker`), формы с `data-validate` подсвечивают все незаполненные обязательные поля (`is-invalid`, снимается при исправлении); `custom.css` — `color-scheme: dark` для полей дат.
- Попутно: автовход после сброса пароля падал 500 с июня (несколько бэкендов) — `post_reset_login_backend` в `mysite/urls.py`.

## Заявка команды на этап (Этапы 1–3 — реализовано 2026-10-17)

План целиком — `~/.claude/plans/team-stage-registration.md` (Этап 2: техника/опции общие для команды, документы из ЛК пилота с его согласия, оплата одной квитанцией или по пилотам; Этап 3: организатор, уведомление пилоту «вас заявила команда» с отказом, заявка в ЛК пилота).

- **Пакет** `applications.TeamStageEntry` (одна на команду и этап, `unique_together`), каждый пилот — обычная `Application(submitted_by_type='team', team_entry=…)`: номера, лимит, документы, УТС, отзыв, экраны организатора — без отдельной логики. Мастер — `applications/team_wizard.py`, шаблон `applications/team_wizard.html`, адреса под `/teams/apply/…` (имя `teams:team_apply` у входа сохранено — на него ведёт кнопка на странице этапа).
- **Шаги:** ① состав — пилоты команды (`TeamMembership` активные) галочками, класс по умолчанию из состава или прошлой заявки, участие, номер (черновик держит `DRAFT_HOLD`); пилот не из состава добавляется **только в заявку** (из базы или новый), в команду не записывается. ② данные пилота + карт + механик (шасси и механик подставляются от уже заполненного пилота пакета; личные данные — из прошлых заявок **этой же команды**, не из профиля пилота). ③ проверка: отправляются все готовые сразу (`finalize_submission` — общая с мастером пилота), обязательные опции добавляются сами, одно письмо организатору и одно менеджеру.
- Доступ — любой действующий менеджер команды (`manager_teams()`); менеджер нескольких команд выбирает команду. `closed_reason()` не учитывает лимит мест (свои черновики его уже занимают) — лимит считается отдельно.
- Командные черновики не попадают в личный мастер (`_find_draft`: `team_entry__isnull=True`) и не считаются дублем для менеджера-пилота (`_duplicate_application`). Страница черновика командной заявки редиректит в мастер команды.
- **Удалено:** старая страница `team_apply` (один пилот, заявка без карта/документов, имя из `full_name.split()`), `team_add_driver` и `/teams/add-driver/` — записывали любого пилота в состав без его согласия; в состав — только приглашением (`invite_driver`).
- ЛК команды: в карточке «Регистрация на соревнования» — таблица заявок команды на этапы.
- **Этап 2.** Документы: решение владельца — **активное членство пилота в команде = согласие** (без отдельной галочки): `vault.vault_profile()` для заявки команды отдаёт подтверждённый `UserProfile` пилота (`verified=True`), если пилот в активном составе (`TeamMembership`) этой команды — документы из его ЛК подставляются при отправке, загруженные менеджером сохраняются в его ЛК (напоминания о сроке — пилоту). У пилота из состава без подтверждённого аккаунта документы хранятся при пилоте (`PilotDocument.driver`, `profile` пустой, `vault.HeldVault`), подставляются в следующие заявки команды и переходят в ЛК при подтверждении аккаунта (`attach_held_documents` из `accounts/signals._sync_roles`; более старый документ того же типа уступает более новому). В неподтверждённый ЛК не пишем — его мог завести кто угодно под именем пилота. Напоминания о сроке — только документам с профилем. Пилот, добавленный не из состава, — без хранилища. Доступ к заявке, документам, квитанции и отзыву — `applications.views.can_manage()`: подавший или любой действующий менеджер команды. Страница «Проверка» (`review`, действия `options`/`payment_mode`/`receipt`/`submit`): опции по каждому пилоту (галочка «всем»), документы всех отправленных пилотов с загрузкой на месте (`next` — только свой хост, `_back()`), оплата — по пилотам или одной квитанцией (`TeamStageEntry.receipt_file` копируется ссылкой в ждущие `ApplicationPayment`, подтверждённые не трогаются; организатор подтверждает по каждой заявке).
- **Этап 3** (`applications/team_notify.py`). После отправки пилоту уходит «Команда N заявила вас на этап» (письмо на аккаунт, если он подтверждён, иначе на email из заявки; несовершеннолетнему — ещё законному представителю; Telegram — если подключён; менеджерам команды не шлём) со ссылкой на отказ `/applications/<id>/decline/<подпись>/` (`signing`, соль `team-entry-decline`, без входа — у многих пилотов нет аккаунта; `@nocache_page`). Отказ = отзыв заявки, письма всем менеджерам команды и организатору. Пилот с подтверждённым аккаунтом видит заявку команды в «Мои заявки на этапы» и на странице заявки (`team_notify.is_team_pilot`, только просмотр + «Отказаться»). Организатор: бейдж «Команда N» (+ «оплата одной квитанцией») и фильтр по команде `?team=` в списке заявок этапа; в Wagtail «Заявки на участие» — фильтр по команде.
- Тесты: `applications/test_team_wizard.py`.

## Документы пилота: постоянные типы, ЛК, напоминания (реализовано 2026-10-15)

- **Постоянные типы** (`applications/document_kinds.py`): Лицензия, Доверенность, Страховка, Медицинская справка + «Другой документ». У документа этапа/чемпионата (`StageDocument`/`ChampionshipDocument.kind`) постоянного типа название, «только несовершеннолетние» (доверенность) и срок действия задаёт тип (`apply_fixed()` в `save()`), организатор выбирает только тип, «обязательный» и пояснение; два документа одного типа на этап/чемпионат форма не даёт. Миграция `applications.0010` перевела старые названия («Мед справка» → «Медицинская справка» и т.п., словарь `NAME_ALIASES`).
- **ЛК пилота** (`accounts.PilotDocument.kind`): один текущий документ на постоянный тип. Файл постоянного типа, загруженный в заявку, копируется в ЛК (`applications/vault.py::save_from_application`), прежний того же типа удаляется (в старых заявках — свои копии). При отправке следующей заявки строки документов заполняются из ЛК по типу (`create_document_rows`), «другие» — по названию; только если документ действует **до последнего дня этапа включительно** и не отклонён. Организатор отклонил файл → `PilotDocument.rejected_at` (`mark_rejected`), сам больше не подставляется. Связь — `ApplicationDocument.vault_document`. Хранилище — только у заявок `submitted_by_type='pilot'` (родитель подаёт из аккаунта ребёнка); за пилотов команд/организаторов в чужой ЛК не пишется. Срок действия для постоянных типов обязателен (и в заявке, и в ЛК) — по нему напоминания. Блок «Мои документы» — инклюд `accounts/_documents_card.html` (ЛК и страница «заявка на проверке», контекст `accounts.views._documents_context`); шаг ⑤ мастера показывает, что подставится из ЛК.
- **Напоминания** (`applications/reminders.py`, команда `send_document_reminders`, реестр `JOBS`): настройки — Wagtail «Организаторы» → «Напоминания о документах» (`DocumentReminderSettings`: сроки «30, 10, 1», письмо, Telegram). Одно напоминание за проход — по ближайшему наступившему сроку, более дальние отмечаются пройденными (`DocumentReminder`, ключ — документ+срок+дата окончания: новая дата начинает отсчёт заново). Пилоту младше 18 — ещё и на `parent_email`. **Менеджерам команд** (все действующие `TeamManager` команд, в активном составе которых пилот) — отдельное письмо/Telegram каждому, с именем пилота и ссылкой на кабинет команды (с 17.10.2026); по документам, хранящимся при пилоте без подтверждённого аккаунта (`PilotDocument.driver`), напоминание получают только менеджеры. Отметка «отправлено» ставится, если дошло хоть кому-то. Неудачная доставка не отмечается — повтор завтра. Проверять на проде только `--dry-run`. Cron: `0 10 * * * cd /www/wwwroot/gripline.ru && venv/bin/python manage.py send_document_reminders >> /var/log/gripline-doc-reminders.log 2>&1`.
- **Telegram без телефона** (`accounts/telegram_link.py`): бот не может написать первым — кнопка «Подключить Telegram» в ЛК → `t.me/<бот обратной связи>?start=link-<код>` (одноразовый, 1 час) → обработчик `/start` в `website/feedback/telegram_bot.py` пишет `UserProfile.telegram_id` (не уникален: родитель подключает себя к аккаунтам нескольких детей). Отправка — `website/feedback/notify.py::send_user_message`; если пользователь остановил бота — `telegram_notifications=False`. После деплоя обязателен `systemctl restart gripline-feedback-bot`.
- **На сайте**: предупреждения в «Мои документы», значок с числом на кнопке «Личный кабинет» в шапке (`accounts/templatetags/document_alert_tags.py`), кнопка «📅 в календарь» — `.ics` с событием на каждый срок и день окончания, будильник в 9:00 (`/accounts/documents/<id>/calendar.ics`, только владельцу).
