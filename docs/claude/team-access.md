# Членство, приглашения и доступ к данным пилота

Реализация ТЗ [v0.2](../team-access-spec.md), исходная версия `889f6718`.
Правила A–C приняты. Production в рамках этой задачи не изменяется.

## Контракт и переход для существующих связей

`TeamMembership` сохраняет состав; `is_active` сам по себе не даёт новых личных прав.
`confirmation_state`: `unconfirmed` — новые неподтверждённые связи; `confirmed` — явное
подтверждение; `legacy` — существовавшие до миграции связи, требующие аудита.
У подтверждения есть дата, пользователь, источник и основание. Неизменяемый из UI журнал
`teams.MembershipConfirmation` сохраняет каждое подтверждение при выходе/повторном вступлении.

Общий сервис `teams.access`: активный менеджер команды ресурса + активное членство без даты
выхода + подтверждение с метаданными. Он используется хранилищем, напоминаниями,
списком пилотов API аккаунта, sync и командным просмотром сессий.
Доступ к текущему хранилищу проверяется от имени фактически работающего менеджера,
а не первого менеджера пользователя или прежнего автора заявки.

**Временный риск:** `TEAM_ACCESS_LEGACY_ENABLED=true` (значение по умолчанию) сохраняет
прежний доступ только строкам `legacy`. Это НЕ подтверждение согласия и НЕ конечный контракт
из матрицы ТЗ. Существующие `is_active` не меняются. Новые строки всегда `unconfirmed` и
не получают доступа даже в режиме совместимости. Сохранение риска необходимо, чтобы default
нового поля не стал массовым отключением состава без аудита. **Строгий выпуск заблокирован до
production-аудита и согласованной классификации legacy.** Для строгого режима установить
`TEAM_ACCESS_LEGACY_ENABLED=false` только после выполнения плана ниже; в тестовых настройках
он уже выключен. Этот PR сам по себе не является разрешением на деплой или переключение режима.

| Сценарий | Раньше | Строгий режим |
|---|---|---|
| Старый результат с командой | Создавал активное членство | Только история RaceResult |
| Новое активное неподтверждённое членство | Хранилище, состав API, привязка, командные сессии | Нет личных прав |
| Явно принятое приглашение | Активное членство | Подтверждение + журнал; доступ команды ресурса |
| Пилот без подтверждённого аккаунта | Одного активного членства хватало | Исключение администратора с основанием и автором |
| Выход / исключение | Деактивация | Деактивация и сброс текущего подтверждения; журнал остаётся |
| Бывшая команда | Копии заявок и иногда текущий ЛК | Только копии своих поданных заявок, без записи в ЛК |
| Владелец сессии | Свои записи | Свои записи независимо от членства и флагов |
| Чужая сессия | Активный состав + два флага | Подтверждённый состав + оба флага |
| Legacy до завершения аудита | Прежний доступ | Временно сохранён только при явно включённой совместимости |

`sync.push` сохраняет прежний контракт: строка принимается, но запрещённый `driver_id`
даёт `AppSyncRecord.driver=None`. Исходный JSON остаётся данными владельца, полномочий не даёт.
UUID принадлежит владельцу записи; сравнение и detail используют ту же область видимости.

Отдельных командных endpoints вложений/экспорта сессий не найдено. Прямая выдача файлов:
`applications.views.serve_document/serve_receipt`, `accounts.views.serve_pilot_document/pilot_document_ics`.
Организатор и администратор платформы сохраняют независимые права. Запись файла командой
в старую заявку не означает право обновить текущий личный документ пилота после выхода.

Проверен установленный `wagtail-cache==3.0.0`: `FetchFromCacheMiddleware` идёт после
AuthenticationMiddleware и пропускает аутентифицированные запросы. Поэтому отсутствие
декоратора само по себе не доказывает утечку. Персональные views дополнительно помечены
`nocache_page`; сессии/detail/compare/analytics уже были помечены. Прогретый кэш и отзыв прав
проверяются с `WAGTAIL_CACHE=True`. При будущей согласованной выкладке нужен штатный сброс
старого page-cache; в рамках задачи кэш production не очищался.

## Read-only аудит и ручной перенос

Production-аудит **не выполнен**: рабочая БД не подключалась. Команда готова:

```bash
python manage.py audit_team_access --dry-run --summary
python manage.py audit_team_access --dry-run
```

Всегда dry-run: флага применения нет. PostgreSQL-транзакция `REPEATABLE READ READ ONLY`;
агрегаты активных/неактивных связей, accepted-приглашений, зависимых командных заявок,
неоднозначностей и пар «результаты без членства». Детализация — только ID связей/команд/пилотов,
ID приглашений и причины, без файлов, имён, email или содержимого документов. Вывод
production хранить в закрытом рабочем месте, не в Git/PR. Аудит запускать на схеме после 0111;
изолированный тест команды проверяет, что записи не меняются.

Accepted-приглашение оценивается по датам, завершённому членству и нескольким периодам.
Даже согласованные даты не доказывают текущее согласие: `joined_at` имеет точность до дня,
старые приглашения не хранят отвечавшего пользователя и перезаписываются при повторном
приглашении. Поэтому legacy не подтверждается автоматически ни при каких комбинациях.

Порядок последующего согласованного выпуска:

1. Отдельный проверенный бэкап БД по `CLAUDE.md`; согласовать окно и план сохранения доступа.
2. Применить только согласованный подготовительный этап схемы/кода с совместимостью,
   получить read-only аудит. Его запуск на production данной задачей не выполняется.
3. Для каждой неоднозначной связи зафиксировать ручное решение. Пилоту с approved-привязкой
   отправить новое приглашение; разрешена повторная отправка и при активной legacy-связи.
   Старое accepted-приглашение не заменяет новый POST. При отсутствии подтверждённого
   аккаунта администратор явно указывает основание и подтверждает отдельную строку состава.
4. Отдельно разобрать дубли периодов и противоречивые даты; ничего не удалять/деактивировать
   скриптом. Для связей, которые не должны получать права, согласовать индивидуальное решение.
5. Повторить аудит, проверить отсутствие неразобранных активных legacy. Только после
   утверждения классификации включить строгий режим. Провести HTTP-проверку матрицы ниже.

## Схема, данные и откат

`website.0111` добавляет поля. При добавлении состояния временный migration-default —
`legacy` для существующих строк, затем model-default меняется на `unconfirmed` для новых.
Это техническая маркировка происхождения, не data-подтверждение. `is_active`, даты, результаты,
документы и сессии не меняются. `teams.0004` создаёт журнал подтверждений. Автоматической
data-миграции accepted → confirmed нет: достоверных доказательств в старой схеме недостаточно.

Предпочтительный откат кода оставляет новые поля/журнал в БД, сохраняя метаданные. Старый код
снова доверяет одному `is_active` и может создавать связи из RaceResult — это возврат уязвимого
поведения, а не безопасное снятие ограничений. Требуется отдельно согласованное окно отката.
Полный schema rollback сначала `teams.0004`, затем `website.0111` удаляет метаданные и журнал:
сначала сохранить их в проверенном закрытом бэкапе. Тест проверяет обратимость структуры и
сохранность членств/active-флагов; обратимость удаления самих метаданных не обещается.

## Ручная проверка в изолированном окружении

1. Создать команды A/B и разных менеджеров. Добавить старый RaceResult: история есть,
   нового членства нет. Новая активная неподтверждённая связь не открывает ЛК/сессии/sync.
2. Открыть приглашение GET: только экран условий. POST без CSRF или от чужого пилота не
   проходит. Правильный POST подтверждает связь; повторный POST не дублирует членство/журнал.
3. В Wagtail «Состав и доступ» проверить фильтр неподтверждённых, источник/дату/автора.
   Для пилота без аккаунта пустое основание не проходит; с основанием появляется событие.
   Существующему владельцу одобренного аккаунта администратор не заменяет согласие.
4. Проверить четыре комбинации видимости сессии и общей настройки. Чужая сессия открывается
   только при двух флагах. Владелец видит свою запись всегда. Подставить чужой UUID и ID пилота.
5. У менеджера A/B проверить точную команду заявки, прямые URL файлов, список и compare.
   Прогреть страницы с кэшем, деактивировать менеджера/членство и повторить запросы.
6. Выйти из команды: текущий ЛК закрыт, старые копии её поданной заявки и доступ организатора
   сохранены. Новая загрузка в копию заявки не заменяет документ ЛК. Получить новое приглашение
   и принять повторно; старое accepted не возвращает права.

Команды и результаты автоматических проверок — [team-access-validation.md](team-access-validation.md).
